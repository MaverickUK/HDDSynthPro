# CLAUDE.md: context for working on IDE Synth Bay

IDE Synth Bay will become an enhanced HDD Synth that emulates the IDE drive itself instead of listening to one. It was called HDD Synth Pro until 10 Nov 2026: use the new name in prose, but the repository, file names (`hddsynthpro.kicad_*`, `hddsynthpro-*.uf2`), identifiers (`HDDPRO_*`), the console's `READY HDDSynthPro` (parsed by `host/hddproto`) and the drive's IDENTIFY model (`HDDSYNTH PROTO`, matched by the rig) keep the old one. It starts as a proof of concept: an Olimex RP2350-PICO2-BB48 (RP2350B) acting as an IDE hard disk behind a USB-IDE adapter. The plan, in thin slices, is in [docs/plan.md](docs/plan.md); the wiring is in [docs/wiring.md](docs/wiring.md).

It follows the approach of [HDDSynth_Native](https://github.com/MaverickUK/HDDSynth_Native): Arduino-Pico under PlatformIO, with core 0 for USB/SD and core 1 for the real-time work. HDD Synth code merges in later; keep the synth out of this repo for now.

The owner is an experienced software architect (C#/.NET, TypeScript, Python) who is new to embedded C++. Explain embedded-specific decisions briefly, and favour clear, idiomatic code over clever code.

## Rules that keep the bus safe

- **Pins:** the pin map in `src/config.h`, `docs/wiring.md` and the tables in `docs/wiring.html` (IDE) and `docs/wiring-sd.html` (microSD), the interactive diagrams, must agree.
  - GPIO 0–1 stay off the bus: the BB48 pulls GPIO 2/3 up to 3.3 V (R17/R18). GPIO 3 is DMACK# (an input; the host drives it) and GPIO 31 DMARQ, wired on the rig since 0.16.2 and on the PCB. GPIO 2 is IOCS16# (open drain, so its pull-up is harmless; wired on the rig since 0.20.0, PCB rev 0.4 plans it), for 16-bit ISA cards: `iocs16.pio` pulls it low while the data register is addressed. It takes `ide_dma`'s PIO block, so it runs only when DMA isn't offered.
  - The PCB (`hardware/`, the RP2350B board in `docs/pcb.html`) keeps the same GPIOs; `hardware/tools/check_netlist.py` checks it against `src/config.h`.
  - GPIO 25 is the LED: the drive build's activity light (core 0's `updateLed()`, `cfg::LED_MIN_MS`).
  - GPIO 0 is the activity link's UART0 TX (`cfg::PIN_LINK_TX`, docs/activity-link.md); GPIO 1 its UART0 RX (`cfg::PIN_LINK_RX`, the synth's `$HDM`, since 0.19.0), with the internal pull-up so it idles high unconnected.
  - DD/DA/CS# must stay on consecutive pins (one PIO read).
  - PCB only (unconnected on the BB48): GPIO 40 SD card detect, GPIO 41 BUS_EN# (the bus switches stay off until the firmware drives it low, which core 1 does once `ide_bus` has set the bus pins up, 0.16.6). First day with the board: [docs/pcb-bringup.md](docs/pcb-bringup.md). PCB rev 0.4 ([docs/pcb-rev04.md](docs/pcb-rev04.md), ordered 10 Nov, its new pins unused by the firmware yet) adds GPIO 32 DASP#, 33 PDIAG#, 42 CSEL (all through the bus switches), 43 SD_PWR# (the card's power switch, pulled down so the card is on), 44/45 CD audio (PWM) and 47 the PSRAM's chip select; 46 is the last spare.
- **Never use internal pull-downs** (RP2350 erratum E9). The host provides the bus pulls.
- **IORDY is open drain:** only pull it low or release it, never drive it high. The host pulls it up to 5 V; PCB rev 0.4 adds a weak backup (R53, 10 kΩ to 3.3 V, header side) for hosts that don't.
- **Slice 0 never drives a pin:** the bus pins stay under SIO control, so the PIO program cannot drive them even if it is wrong. Driving starts in slice 1, and only on DD (during reads of the drive's own registers), IORDY, INTRQ (both ways while selected with nIEN clear, 0.19.1: ISA cards have no pull-down), IOCS16# (open drain, GPIO 2) and, during a DMA command only, DMARQ (GPIO 31, `ide_dma`; its output is forced off otherwise).
- **`ide_bus`'s PIO block holds `iordy_watchdog` too** (loaded always, started only with `isa = on`), so nothing else lands there: the diagnostics' `iordy_check` would see DIOR# through `ide_bus`'s synchroniser bypass. With the data lane (`early_answers = off`, `isa = off`, [docs/data-lane.md](docs/data-lane.md)) the block holds `ide_bus_data` and `ide_data_in` instead, filling its 32 instructions: no watchdog, so ISA cards need `isa = on`.
- **DD0-15 belong to one PIO block at a time** (GPIO function select): `ide_bus`'s, except during a multiword DMA read burst, when `ide_dma` hands them to its own block and back after it. On the lane two state machines in that block share them: only one drives DD in any access, and `ide_bus_data` releases them after every read.
- **Timing:** IORDY must go low within 35 ns (tA) of a strobe. Trigger on the chip-selects, which are valid 70 ns earlier (see the plan). ISA IDE cards decode the chip selects from the address alone (memory and refresh cycles assert them too) and pass IORDY to IOCHRDY, so IORDY held at a chip select with no strobe froze an ICL 386 for good: with `isa = on` (0.22.0) `iordy_watchdog.pio`, in `ide_bus`'s PIO block, releases IORDY once it has been held 23 µs (the BIOS left up to 11 µs between a status read and its data, with the drive selected). Tried and dropped: IORDY only at the strobe (0.21.0: too late for that bus), countdowns in the bus program (0.21.1-0.21.2: too short, and a 60 ns release can't beat the host's pull-up).
- **Core split:** core 1 runs the bus loop and never touches USB, SD or anything slow. Everything it runs per access is marked `CORE1_RAM`, because code in flash can stall it for tens of µs; `scripts/check_core1_ram.py` (run by `rig.sh` and CI) fails if `loop1` can reach flash. Share flags with core 1 as `SharedFlag`, not `std::atomic<bool>`, whose members GCC may call out of line from flash. Slow work happens while STATUS shows BSY, never behind IORDY. Core 0 must keep up too: work it does per bus event (like the IORDY timer's reports) has to be cheap and bounded per call, or read-aheads are late and core 1's PIO accesses are held up (0.8.24). Core 1's speed also depends on where its code sits in RAM: a change elsewhere can move the fast lane and change how many reads wait, so benchmark reads (`-m speed`, or 4 MB sequential) after any core 1 change. `scripts/core1_layout.py` (a PlatformIO post script) puts the hard disk's core 1 code (`CORE1_RAM`) first in RAM, file by file in a fixed order, so no other code can move it; the CD-ROM's (`CORE1_RAM_CD`) goes after `.data`. `scripts/check_core1_layout.py` (CI; a warning in `rig.sh`) fails if any of it moved or changed against `scripts/core1_layout/<env>.txt`: benchmark, note the result in `docs/speed-log.md`, then record the new layout with `--update`. A new file with `CORE1_RAM` code goes in `core1_layout.py`'s list. Core 1 runs a queued command as soon as it has served the access, never waiting for an empty FIFO: back-to-back status polls once kept a command queued for good (0.29.0-2d.4). `check_core1_ram.py` also catches SDK `static inline` helpers GCC leaves out of line (`pio_sm_set_enabled`, `dma_channel_abort`, `pio_sm_restart` did): write the register accesses out where it flags one.

## Toolchain

- **Build:** `pio run` (PlatformIO lives in `~/.platformio-venv/bin/pio` on the dev Mac, `~/.platformio/penv/Scripts/pio.exe` on Windows; `rig.sh` looks in both). The board is `olimex_pico2bb48`. There are three builds (since 0.32.0, [docs/one-build-per-board.md](docs/one-build-per-board.md); `bb48_cdrom` and `bb48_hdcd` were folded in), selected by `FIRMWARE_SLICE` and `HDDPRO_PCB`:
  - `bb48` (0): listen only;
  - `bb48_drive` (3): the drive, slices 1–5. By `HDDSYNTH.INI`, a hard disk as device 0 with a second disk, a folder or a CD-ROM drive as device 1 (`device1 = cdrom`), or a CD-ROM drive alone as device 0 (`device0 = cdrom`): `hdcd::Device` (`hdcd_device`, over `ata_device` and `atapi_device`/`mmc`, [docs/atapi.md](docs/atapi.md)), which `drive_device.h`'s `DriveDevice` names. The CD-ROM serves an ISO or a BIN/CUE's data track (`cue_sheet`), PIO or (when offered) multiword DMA for PACKET's data; as device 0 on early answers or `ide_bus` (never the data lane), as device 1 on `ide_bus`. Per access the CD-ROM costs `cdSelected()`, one mask and one compare;
  - `pcb_drive` (3, `HDDPRO_PCB`, since 0.31.0): `bb48_drive` for the IDE Synth Bay PCB, with the SD card on 4-bit SDIO (about four times SPI; the BB48's hand-wired leads couldn't carry it). `pio_plan.h` shares out the PIO blocks: SDIO takes one, so with DMA offered the diagnostics are off. A card left in SPI mode by other firmware runs over SPI until it's taken out and put back (`S` says so).

  `main.cpp` holds them all. Rig tests skip unless the board runs the build they need (the CD-ROM's, by `S`'s `CONFIG device0=... kind=cdrom` line), and `scripts/rig.sh` takes `PIO_ENV`.
  - The variant defines `PIN_LED` as a macro, so don't reuse Arduino pin-macro names for constants.
  - The clock is 200 MHz (`board_build.f_cpu`, since 0.14.0), and `setup()` keeps the peripheral clock (SPI, UART) on it. Anything timed in cycles must say which clock: `pio_sim.CLOCK_HZ` matches the firmware's, and C++ works cycle counts out from `clock_get_hz(clk_sys)`.
- **PIO programs:** the platform assembles each `src/*.pio` into a `.pio.h` next to it (git-ignored) before every build. Include them as `"name.pio.h"`.
- **Host unit tests:** `test/run_native_tests.sh` (plain `c++` with ASan/UBSan). Keep `bus_sample`, `trace_format`, `spsc_ring`, `identify`, `ata_device`, `gen_disk`, `block_source`, `fetch_mailbox`, `short_test`, `activity`, `activity_link`, `drive_config`, `sector_check`, `media_watch`, `welcome_disk`, `seek_timing`, `image_parts`, `mmc`, `atapi_device`, `hdcd_device`, `cue_sheet`, `card_retry`, `command_history` and `pio_plan` free of Arduino and SDK headers so they stay testable here.
  - `drive_params.*`, `drive_timing.*` and `sentence.*` are **copies from HDDSynth_Native's `src/`** (the modelled drive's presets, its seek/rotation/transfer timing and `$HDM`, and the sentence helpers), unchanged, so seek timing agrees with what the synth plays; HDD Synth's tests hold `seekTimeUs()` to its engine. Change them there and copy them back; the version copied is in its git history (0.19.0 copied HDDSynth_Native 6a68a71, its v0.21.0). When touching the ring, the mailbox or the fetch handshake, also run `SANITIZE=thread test/run_native_tests.sh`.
- **CI:** `.github/workflows/build.yml` builds the firmware and runs the C++ tests and `pytest -m sim` on every push. A `vX.Y.Z` tag that matches `FIRMWARE_VERSION` publishes a release with the UF2.
- **Python tests:** in `host/` (pytest). One marker per slice; `sim` needs no hardware.
  - Plain `pytest` runs only the `sim` tests.
  - `host/hddproto/pio_sim.py` simulates the PIO instructions the programs use and runs the real `pioasm` output. Extend it when a program uses a new instruction, rather than letting it guess.
  - `host/hddproto/ide_host_model.py` is a PIO host (modes 0-4) that honours IORDY. `tests/test_pio_bus_sim.py` uses it to hold `ide_bus.pio` to modes 0-3's timings, and the sim must be configured as `ide_bus.cpp` configures the state machine.
  - `host/hddproto/mdma_host_model.py` is a multiword DMA host; `tests/test_dma_sim.py` holds `ide_dma.pio` (the DMA data phase, [docs/dma.md](docs/dma.md)) to MDMA modes 0-2's timings. `pio_sim.assemble(..., program=)` picks one program from a file that holds several.
  - After a `git stash`/checkout that rewrites a `.py` within the same second and at the same size, Python can keep running the old one from `__pycache__`: delete the caches if a result looks stale.
- **On the rig:** `scripts/rig.sh -m sliceN` runs the unit tests, builds, flashes and runs the rig tests.
  - Evidence goes to `host/runs/` (git-ignored); reference traces live in `host/reference/`.
- **Benchmark image:** `tools/bench-image/build_image.py` builds `DOSBENCH.IMG` (FreeDOS and `HDDBENCH.COM`, from `hddbench.asm`, NASM), the standard disk for retro PCs. `test_qemu.sh` boots it in QEMU in Docker (Homebrew has no QEMU for macOS 14) and prints its `BENCH.LOG`. Layout and pattern: its README.
- **Rig** (the Windows PC, from an administrator Git Bash; the Mac's setup up to 0.26.2 is in `CHANGELOG.md`):
  - **The adapter** shows as USB `152D:2338` (JMicron) on Windows and `2537:1081` (Norelsys NS1081) on the Mac: the same unit, serial `984220294922`; why it enumerates differently isn't known. USB-powered (its brick only powers a drive plugged into it). Its 44-pin header shares the bus with the 40-pin one, so the listen build on the 40-pin can record a real drive on the 44-pin. A real CF card works through it. A second NS1081 (serial `0123456789ABCDE`) never detected the drive: its IORDY floats, it seems. So the rig has **one working adapter**.
  - **It declines:** after hours to days of use it garbles its own USB serial (low bits of characters cleared: `084200294902`, `002200220022`), the drive's name and its detections, although the bus observer sees every IDENTIFY right on the cable. Replugging it helps for minutes; restarting the PC clears it. If cycles fail more and more, in every build, restart the PC before blaming the firmware.
  - **Re-detection without a replug** (0.11.0): console `V` takes the drive off the bus, the host's next read fails, the adapter resets and probes, and the drive comes back at its first RESET#: IDENTIFY, SET FEATURES, the read retried. About 30 s; the host keeps the disk. `HDDPRO_REPLUG=redetect` makes `rig.replug()` do this, so slices 1-2 run their 20 cycles unattended.
  - **A fresh power-up probe needs a physical replug:** nothing scripted cuts its VBUS (`uhubctl` re-enumerates it on the Mac's Realtek hub; `pnputil /restart-device` on Windows). After Windows drops the disk, `pnputil /restart-device` on the adapter's current instance brings it back; Windows takes the adapter's list of drives (LUNs) only then, so a device 1 found by a re-detection appears after it.
  - **With a CD-ROM configured:** after the drive restarts (a flash, `!`, `T`, `J`, `P`) the adapter goes silent until a physical replug. It sets the DMA bit on every PACKET, so the CD-ROM needs `mode = mdma2` and `dma = on`; without, the drive refuses them and the adapter resets it every 20 s and shows neither drive. Windows polls the CD-ROM once a second (GET EVENT), which the rig tests' `wait_quiet()` ignores. Its raw device is `//./CdRomN` (`MSYS_NO_PATHCONV=1 HDDPRO_CDROM_DEV=//./CdRom1`; N changes as it re-enumerates).
  - **Detection:** it asks for PIO flow-control mode 4 (SET FEATURES 03h, 0Ch) whatever IDENTIFY offers, then the fastest mode offered (PIO 3: 0Bh, else mode 0: 08h; never 1 or 2), or MDMA 2 when offered. It never sends FLUSH CACHE and ignores multiple mode.
  - **Its pace:** in PIO it reads about one data word per 1.1 µs whatever the mode, and waits about 10 ms after each READ command before polling, so faster PIO modes can't speed reads up; multiword DMA avoids both (a 64 KB read costs 0.11 ms plus the data).
  - **With no drive answering** it pulses RESET# every 4.8 s (a double pulse first) and runs the register check (A5/5A/AA/55) about 420,000 times a second, so the listen build drops events: its capture window (`w`) keeps a window after each RESET#.
  - **Standby:** it sends CHECK POWER MODE, then STANDBY if the drive says active, from macOS only (Windows never does, so soaks from Windows don't test it). Waking (IDLE IMMEDIATE) must show BSY before the interrupt, or the adapter hangs.
  - **After a read error** (UNC) mid-transfer it goes silent about 60 s until the host resets it, then re-detects. A card pulled and put back: see `-m card` and 0.13.0 in `CHANGELOG.md`.
  - **Windows** can keep a switched-out disk's partitions mounted and refuse raw writes inside them (`EBADF`); `host_windows.open_raw` runs `Update-Disk` first. **On the Mac:** match disks on diskutil's `IORegistryEntryName` (the adapter splits the model at the first space); after `V` it can give the disk an empty name until a replug; serve the test disk (`T`) or `HDDBENCH.IMG` (`J`) before the adapter goes on, or Spotlight writes to the image.
  - `host/rig.env` (git-ignored, from `rig.env.example`) holds the replug settings, and `scripts/rig.sh` loads it.
- **Host OS:** the rig runs from macOS or Windows. `host/hddproto/host.py` holds what's common (replug, `find_disk`, `pread`/`pwrite`, which Windows lacks) and `make_host()` picks `host_macos.py` or `host_windows.py`; OS-specific code stays in those two. Tests use `make_host` and `hddproto.host.pread`/`pwrite`, never `os.pread`. Slice 6 adds a Linux host for pass-through.
  - macOS: there's no `O_DIRECT` (use `/dev/rdiskN`), no `dmesg` (use `log show`), and no ATA pass-through.
  - Windows: `\\.\PhysicalDriveN` (uncached), found with `Get-Disk`; it needs an administrator terminal. Run `scripts/rig.sh` from Git Bash. pyserial doesn't report the USB product there, so `find_port` falls back to the only port with the board's vendor ID (Olimex 15BA, or Raspberry Pi 2E8A), or `HDDPRO_PORT=COMn`. uhubctl hardly works, so replugs are by hand. The native C++ tests need WSL (no ASan/TSan); `rig.sh` skips them without a `c++`. Windows never sends the USB disk STANDBY (not even with the disk timeout at 1 minute), so soaks from Windows don't test standby and wake. Pause Windows Update before a long soak: it restarted the PC 6 h into one.

## Drive data path

Core 1 owns `ata::Device` and never waits. For a read:
1. The device sets BSY and exposes a `Fetch` (id, LBA, its sector buffer).
2. Core 1 posts it once to `FetchMailbox`.
3. Core 0 fills the buffer from a `BlockSource` and posts the result.
4. Core 1 calls `fetchDone()`, which sets DRQ, unless the id is stale after a reset.

A write (WRITE SECTORS) runs the other way: DRQ first, the host writes 256 words into the buffer, then BSY and a `Fetch` with `store` set, which core 0 writes to the `BlockSource`.

With `seek_timing` on (`src/seek_timing.*`, docs/activity-link.md), core 0 keeps each result until the modelled drive would have the sector (`Fetch` carries the command's first LBA and count for it), checking on each loop pass; the drive shows BSY meanwhile, never IORDY. Off, results go at once.

The device doesn't touch the buffer while BSY. Core 0 must never block for long: it serves fetches before and between trace prints, and only prints when USB serial has room.

The disk is the image `HDDSYNTH.INI` names (`docs/settings.md`, `src/drive_config.*`; `HDDSYNTH.IMG` by default), or `HDDSYNTH.IMG` if that one can't be used, on the SD card (`ImageDisk` over SdFat, `src/sd_card.*`), else `RamOverlayDisk` (writes stay in RAM, up to 512 sectors, until reboot) over the welcome disk (`src/welcome_disk.*`: a FAT16 volume computed per sector, holding `README.TXT` from `welcome/README.TXT`, embedded by `scripts/embed_welcome.py` into the git-ignored `src/welcome_text.h` before each build, and the sample `HDDSYNTH.INI`), or over `GeneratedDisk`, the test disk, with `device0 = none` or console `T` (`disk=generated`; the bus observer checks data only there). Core 1 waits at boot for core 0 to choose it. Never format the SD card or touch files on it other than the image being served, the scratch `HDDBENCH.IMG` and `HDDSYNTH.INI` (which the owner allowed the firmware to create and edit, with console `C`/`E` only): it holds the owner's data. Benchmarks that write use `HDDBENCH.IMG` (`disk=bench`). Slices 3–4 and the soak skip on an image, since they write to it, and on the welcome disk: for them, `T` (no card needed; then replug the adapter), or `E device0 = none` and `!` serve the generated disk with the card in (0.12.0), and `E device0 = HDDSYNTH.IMG` and `!` put the image back.

The bus program holds IORDY on a write while its RX FIFO is full, so a write burst can't outrun core 1. `ide_bus.pio` fills its PIO block's 32 instructions.

## Activity classification

`src/activity.*` (pure C++, `test_activity.cpp`) classifies media commands as sequential or seeks, and the recent mix as IDLE/SEQ/RAND, for the HDD Synth's sounds.
- It runs on core 0, fed from the CMD/DONE events as they leave the trace ring.
- It prints `ACT` lines on each change.
- Thresholds are in `activity::Config`.
- To tune on recorded traces: `.pio/native-tests/classify_trace < trace.txt`.
- Rationale and limits: `docs/activity.md`.

## Trace format

Core 1 records events into an SPSC ring, and core 0 prints them (`src/trace_format.h`).
- Identical consecutive accesses are merged into one `EV` line with a count.
- The drive build logs commands as `CMD`/`DONE` lines (device 1's `CMD` lines end in `d1`); raw accesses only after `t`.

The Python parser is `host/hddproto/trace.py`; change both together.

Console:
- `h`: help, and the READY line with version and build;
- `p`: pin levels (wiring check);
- `s`: stats; on the drive build also `iordy_slow`/`iordy_max_ns`/`iordy_max_reg`/`iordy_max_at_us` (reads IORDY held over 400 ns, and the longest: how long, which register, when; measured by `iordy_timer.pio`) `iordy_early` (reads that started before IORDY was low; in PIO mode 3 most do, harmlessly) `iordy_ignored` (reads the host ended while IORDY was still low, so it didn't wait: should be 0; a `NOIORDY` line if not, `iordy_check.pio`, naming the command it fell in or followed and when; `iordy_ignored_data` the data register's) `iordy_data_slow`/`iordy_data_max_ns` (data register reads held past 400 ns, by 700/1,000/1,250 ns and longer, and the worst), `bus_sectors`/`bus_bad`/`bus_gaps`/`bus_dma_words`/`bus_ring_max`/`bus_dropped`/`bus_lost`/`bus_checks` (the bus observer's check of data sectors on the cable, against the generated disk; a bad one prints `BUSERR`. `bus_checks=spot` (the default): the drive comes first, and samples the checks can't keep up with are dropped (`bus_dropped`), or after a possible overrun (`bus_lost`): every sector of PIO and short DMA commands is checked, a few percent of long DMA transfers. `full` (console `O`): every sector, slowing DMA reads to about 2 MB/s. `bus_ring_max`: the most samples ever waiting, of 4,096) `bus_identify`/`bus_identify_bad` (IDENTIFY blocks checked on the cable against the drive's own; on an SD image only for 10 s after each RESET# release, since checking every word slows reads; a bad one prints `BUSERR t IDENTIFY ...`) and `bus_contested`/`bus_stalls` (fast peripheral bus contention), `dior_no_cs` (DIOR# with no chip select while no DMA is offered: an ISA card passes every I/O read the PC makes, a PCI controller none; evidence for choosing the bus program by itself, `n/a` while DMA is offered; a `NOCS` line gives the first after each RESET# release, in ms), plus `write_behind`, `image_name`/`config`, `card`/`card_lost`/`card_back`/`card_restarts` (the card the image is on: `present`, `lost` after a failed read or write, `changed` if a different card or an edited image came back; `CARD lost|back|changed` lines on each change, and `CARD lost and back` or `CARD restarted` for a card that stopped answering and was restarted at once, by device 0's or device 1's reads, `S` or `M`) (the image served, and the settings file as read at start-up). Every read held past 1,250 ns also prints `SLOWREAD t register ns` (the time is when core 0 collected the report), and a command running over 3 s prints `STUCK` (the last fetch core 0 served, and whether its result is still waiting for core 1);
- `r`: reset the read timings (they also restart when the host releases RESET#);
- `t`: raw bus trace on or off;
- `D` then a digit: debug, answer data reads that many × 250 ns late (`-m timing`; `D0` is off);
- `F`: debug, core 1's fast lane for data reads off or on (to compare);
- `A`: read-ahead off or on until a restart (`read_ahead` in `HDDSYNTH.INI`);
- `m`: print a `MARK` timestamp (used by the activity rig test);
- `S`: start the microSD card and report it, then `CONFIG` lines: the settings from `HDDSYNTH.INI`, the image served, why a configured image wasn't used, warnings (drive build; only reads);
- `C`: create `HDDSYNTH.INI` with the defaults if it isn't there; `E` then `key = value` and Enter: set one setting (`device0`, `device1`, `mode`, `dma`, `write_behind`, `read_ahead`, `activity_link`, `seek_timing`, `isa`, `early_answers`, `iordy`, `geometry`), keeping the rest of the file; `!`: restart, to apply them (keeps `J` or `T`);
- `I`: create `HDDSYNTH.IMG` (64 MB, zeros) on the card if it isn't there; reboot to use it;
- `K`: create `HDDBENCH.IMG`, the scratch image for benchmarks that write; `J`: restart serving it, or back (kept in a watchdog scratch register, so a power cycle always returns to `HDDSYNTH.IMG`); `T`: restart serving the test disk, card or no card, or back (the same register, so `T` and `J` undo each other);
- `L`: the activity link on or off until a restart (`activity_link` in `HDDSYNTH.INI`; `s` shows `link`, `link_sent` and `link_last`, `head_sent`/`head_replaced`/`head_last` for `$HDE`, and `hdm_valid`/`hdm_rejected`/`link_rx_errors` for the synth's `$HDM`);
- `U`: the link's loopback test, with a jumper from GPIO 0 to GPIO 1: `$HDA` and `$HDE` read back, and one `$HDM` sent and read back (`LOOPBACK pass|fail|no-data ... head_sent= head_valid= model=ok`; `-m link`);
- `H`: seek timing off or on until a restart (`seek_timing` in `HDDSYNTH.INI`; `SEEKTIMING on|off`; `s` shows `seek_timing`, `seek_active`, `seek_rpm`, `seek_actuator`, `seek_commands`, `seek_held`, `seek_avg_us`, `seek_max_us`, `seek_total_us`, `seek_capped`; `-m seek`);
- `V`: the drive leaves the bus (`ABSENT on`) until the adapter's next RESET#, a second `V`, or 120 s (`ABSENT off ...`); for re-detection without a replug (`HDDPRO_REPLUG=redetect`);
- `P` then `e`, `l`, `i` or `0`: the bus program (early answers, the data lane, `ide_bus`, or the settings') until a power cycle, whatever `HDDSYNTH.INI` says; restarts (watchdog scratch 1, as `J`/`T` use scratch 0); `S` says so with a `CONFIG bus program set from the console` line;
- `M` then a disc and Enter (CD-ROM builds): the CD-ROM's disc until a restart: an ISO's name, `test` (the test disc) or `none` (eject); `DISC NAME frames=N` or `DISC none` when done. Core 0 ejects, waits for core 1 to take it (once the device is idle), swaps the file, then inserts, so no fetch for one disc is served from the next; the host gets a removal event, then new media and a unit attention (28h);
- `O`: the bus observer's full checks on or off until a restart (`OBSERVER full|spot`; spot checks by default, full checks slow DMA reads to about 2 MB/s; the soak turns them on);
- `W`: write-behind on or off until a restart (on by default since 0.17.0; `write_behind` in `HDDSYNTH.INI`);
- `x` then `Y`: the solder-bridge test, IDE cable unplugged (`short_test.*`; the board reboots afterwards);
- `w` (listen build): the capture window on or off: each RESET# assert opens a window of `cfg::LISTEN_WINDOW_EVENTS` accesses, the rest are counted (`skipped=` in `s`) but not recorded (`-m slice0` uses it);
- `b`: reboot to the bootloader.

## Versioning

SemVer in `src/version.h` (`FIRMWARE_VERSION`, plus `FIRMWARE_SLICE`). Bump it with any firmware change, add a `CHANGELOG.md` entry (Keep a Changelog), and tag `vX.Y.Z`.

  - Status reads past ATA's 1,250 ns, all waited for (`iordy_ignored` 0): early answers reach 2,110 ns (so slice 1's IORDY check fails on every build since 0.28.0, and the soak needs `HDDPRO_SOAK_IORDY_MAX_NS=2500`); with a CD-ROM, Status and Device reads reach 3,600-5,550 ns; the data lane holds about 1,400 Status reads a benchmark past it during writes ([docs/data-lane.md](docs/data-lane.md)).
